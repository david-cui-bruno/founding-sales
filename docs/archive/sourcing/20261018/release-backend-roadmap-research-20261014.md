Do not change the older production role policy to match a prospective Terraform template. The supplied 13:15 UTC dated metadata snapshot reports a `NoDeploymentDataAccess` explicit deny on `s3:GetObject*` and no attached policies; that conflicts with assuming template grants are deployed or sufficient. Any permission reconciliation must preserve that actual older policy and separately review a narrowly scoped exception or attachment path.

This is an engineering recommendation to avoid a needless encryption migration, not authorization to change IAM, backend config, or encryption. The actual approved role, policy attachments, effective denies, and state encryption must be read back under an explicitly authorized operation before bootstrap or held-backlog application.

## Required permission shape and failure modes

Terraform's S3 backend requires `s3:ListBucket` scoped to the state prefix, and state-object `s3:GetObject`/`s3:PutObject`. With native `use_lockfile`, the `.tflock` object separately needs `GetObject`, `PutObject`, and `DeleteObject`; state itself does not need `DeleteObject`. Production config also enables DynamoDB locking, whose documented actions are `DescribeTable`, `GetItem`, `PutItem`, `DeleteItem`. Terraform's S3 backend implementation additionally records/checksums state MD5 in DynamoDB, so the backend caller needs the relevant scoped row read/write/delete operations, not merely lock-table discovery. Scope DynamoDB access to the lock and state checksum key rows, and S3 list/object permissions to the one existing production backend key and its lock object. [Terraform S3 backend permissions](https://developer.hashicorp.com/terraform/language/backend/s3#permissions-required); [Terraform v1.15.8 S3 backend client: state writes, lock writes, and DynamoDB MD5 rows](https://raw.githubusercontent.com/hashicorp/terraform/v1.15.8/internal/backend/remote-state/s3/client.go#L180-L220) [lock](https://raw.githubusercontent.com/hashicorp/terraform/v1.15.8/internal/backend/remote-state/s3/client.go#L321-L375) [MD5](https://raw.githubusercontent.com/hashicorp/terraform/v1.15.8/internal/backend/remote-state/s3/client.go#L549-L625).

For explicit `kms_key_id`, Terraform's documented backend contract requires `kms:Encrypt`, `kms:Decrypt`, and `kms:GenerateDataKey` on that key. The pinned v1.15.8 code sends SSE-KMS on both state and lock uploads; therefore a planner with only `kms:Decrypt` can read/decrypt state but cannot successfully write an SSE-KMS-encrypted lockfile. That is a real init/lock acquisition failure, even before any resource plan. KMS permissions must be scoped to the selected key and authorized separately for each backend caller that writes locks; KMS key policy must also allow the principals. Do not add broad KMS permissions or select SSE-KMS by implication. [Terraform S3 backend `kms_key_id`](https://developer.hashicorp.com/terraform/language/backend/s3#s3-state-storage); [pinned client state encryption](https://raw.githubusercontent.com/hashicorp/terraform/v1.15.8/internal/backend/remote-state/s3/client.go#L190-L209); [pinned client lock encryption](https://raw.githubusercontent.com/hashicorp/terraform/v1.15.8/internal/backend/remote-state/s3/client.go#L332-L353).

AWS evaluates all applicable policy types and an explicit deny overrides an allow. Thus the supplied `NoDeploymentDataAccess` deny for `s3:GetObject*` blocks a matching state-read allow; adding or attaching the source template alone cannot fix it. The narrow exception (if approved) must preserve the older deny elsewhere and be specifically conditioned/scoped to the existing backend state object and only the required backend principals/actions. Validate the actual policy composition, permissions boundary/session policy/resource policy, and role trust; a policy document allow is not effective access proof. [AWS IAM policy evaluation](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html).

## Minimum repeatable contract before bootstrap / #552 rollout

1. Record one explicit backend encryption choice per root and keep runtime config, policy, documentation, and evidence aligned. **Recommendation:** retain current AES256/SSE-S3 behavior: `encrypt = true`, omit `kms_key_id`, avoid introducing a new KMS dependency, and preserve observed state rather than rewriting/migrating it. This is not a claim that bucket defaults or future writes have been verified. If an owner instead approves SSE-KMS, pause and specify the exact key, key policy, caller grants for `Encrypt` + `Decrypt` + `GenerateDataKey`, and state/lock read/write path first. Treat it as an intentional contract change, not an optional hidden init flag.
2. Name, for each actual caller, its backend role and separate Terraform provider role; identify the exact workflow/command using each. Source names planner, reviewed apply, and maintenance role-ARN secrets, but does not prove their live values or attachments. At minimum review the planner and reviewed apply identities, David's local human planning identity, and confirm routine maintenance does not initialize Terraform. Reconcile the exact deployed older policy and attached policies with source, including the explicit-deny exception; do not wholesale replace it with the prospective template.
3. Keep state read/write and lock permissions separate: the read-only planner needs state-object and checksum-row reads plus lockfile and lock-row acquire/release rights, not checksum writes merely because it can lock. The reviewed applying caller additionally needs the state and checksum writes used by its reviewed flow. Scope each action to its corresponding existing key/row. No application deploy role gets backend access absent an explicit, separate need. No S3 state `DeleteObject` grant is needed for Terraform's backend.
4. Add source-controlled positive/negative policy/config checks: exact bucket/key/lock/table/key scope; only listed caller roles; state write/delete distinction; lock writes included; deny remains effective outside the explicit carve-out; no KMS permission when AES256 path is selected; KMS writes fail closed if SSE-KMS is selected without all three permissions. A local policy simulator/model and Terraform policy tests are useful regression checks, but do not prove the live role's effective authorization or successful backend transaction.
5. Before a real bootstrap/apply, require a separately approved, exact reviewed operation and readback: actual state encryption, role trust and attachments, all applicable policies/denies, key policy if relevant, and backend access using the intended identity. Then only the authorized reviewed plan/apply can prove real init, state read, lock acquire/release, checksum consistency, and narrowly scoped state write behavior. No such operation is approved by this note.
