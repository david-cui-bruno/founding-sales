## Audit findings

- Production app-only deployment is already automated in `.github/workflows/greenfield-deploy.yml`. The schema88 production release and signed1.0.51 publication succeeded. Recent repeated blockers arose in the separately provisioned diagnostic, not evidence that ordinary deployment is generally failing.
- Schema/infra/protected changes use the existing manual sequence. Caller coordination is unnecessarily broad, but migration compatibility, sending drain, saved plan and ambiguous-write reconciliation remain necessary. Current exact schema ranges mean rolling back binaries alone cannot undo a migration.
- Settings already discover candidate authority and provide Activate/Disable: `apps/desktop/src/renderer/settings/CrmCapabilitiesSection.tsx`. Creating another activation UI from scratch duplicates shipped source. The actual gaps are generic readiness reasons and assembling trusted evidence/authority.
- `packages/domain/crm/capabilityAuthority.ts` binds authority to exact schema/implementation/image/configuration. A new deployment can invalidate authority. Revalidation/receipt refresh should be automated; it is not automatically a requirement to reacquire Gmail consent or rerun unchanged model-quality evaluations. Changed purpose/account/scope/model/data handling or affected implementation requires relevant new evidence. Any relaxation of exact runtime binding requires explicit design/ADR approval.
- The runtime checks receipt structure, fingerprints, trusted role and current referenced bindings; it does not independently fetch all semantic evidence behind review-reference strings. A trusted assembler must validate those artifacts and keep its reviewer/provisioning path distinct from application settings. Merely filling strings would not simplify verification truthfully.
- #547 remains real OAuth, two original messages, read/delete/revoke and cleanup acceptance. AWS provisioning is an implementation of the current isolation decision; fixtures or a browser glance cannot replace actual product-path provider behavior.
- #466 mixes a completed signed release with unfinished notifications/restart/sleep-wake/reply-preview acceptance. #547–#552 contain stale source-version text. Ticket bodies need current remaining-work contracts, with dated evidence linked separately.

## Approved decisions — October11

1. Recommended acceptance location: disposable local API/worker/PostgreSQL with actual Google transport and the dedicated nonproduction project; no permanent staging. Explicitly revise ADR0010 before use. Google supports localhost callbacks; local real-Google/encryption composition and truthful isolation bindings still need source work. [Google web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server).
2. Recommended first-user AI posture: distinguish deterministic progress from hosted extraction; allow David-only hosted features after critical synthetic/control tests, actual model integration, a reviewed labeled set and scoped spend/data consent, with visible provisional quality and continuing real-example review. Do not claim representative sales reliability. This is a proposed policy change: current actual_representative requirement stays effective until explicitly approved and implemented. Broad user rollout remains a different decision. Meaningful small evals plus real-failure accumulation are supported by [Anthropic agent eval guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), not proof our system passes.
3. Recommended operator flow: preserve app-only automation; one reviewed protected Deploy journey; one stated-scope Enable action backed by automatically assembled, independently reviewed evidence. No compulsory second human; no self-authorizing application settings. Local integration success is separate from deployed runtime configuration and native OS acceptance. Keep exact bindings and automate evidence reuse/rebinding rather than relax them implicitly.
