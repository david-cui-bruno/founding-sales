# Managed LinkedIn publishing: Buffer first, Typefully alternative

Decision note: 2026-11-05. Scope: David's personal LinkedIn profile, three genuine posts/week, text or text plus one approved image; issue #935 under #783. Primary public documentation only. No signup, account access, credentials, app connection, API calls, publishing, paid calls, infrastructure changes, or repository checks were performed. Typefully's public pricing page was rendered in a separate unsigned-in managed browser because its static response omitted the plan table.

**Selected outcome:** David chose **our custom app + Buffer Free**, retaining existing Bedrock drafting and accepted calibration rather than adding Dots/Muse. [ADR0040](../adr/0040-buffer-managed-social-publication.md) records the cutover; [current state](../operations/current-state.md) owns implementation, actual account acceptance and deployment. This choice does not activate a plan or authorize a paid upgrade.

## Recommendation

**Try Buffer Free before expanding the custom remote-browser host.** Buffer documents personal-profile automatic publication, a current API available on Free, draft/schedule/read/delete operations, and an official MCP server. Its ten *simultaneously scheduled* posts per channel can support a rolling three-post/week queue; unlike Typefully Free's ten *posts/month*, it is not a monthly publishing ceiling. Buffer explicitly says it handles social-network publication after the API handoff. This is a documented managed-service route, not a claim that our own self-service LinkedIn app acquired new scopes. [B LinkedIn][B pricing][B API FAQ]

**[INFERENCE] A successful Buffer pilot could remove our need to maintain a LinkedIn posting browser host:** keep the existing source-grounded writing/calibration workflow and hand approved content to Buffer; Buffer owns the network-facing scheduler. It would not remove human OAuth/reconnection, content decisions, monitoring, or unresolved-attempt handling. Actual account eligibility, app entitlements, API/MCP availability in our environment, connectivity, and successful publication remain **untested**. Neither scheduler nor a cloud agent is evidence of a bypass for the observed provider security denial.

The [2026-11-03 self-service note](social-linkedin-publication-options-20261103.md) remains applicable to that route. Its restricted-member-read and self-service unattended-agreement gaps must **not** be automatically attributed to managed providers. Conversely, vendor documentation of routine scheduling is not independent inspection of a vendor's LinkedIn partner agreement or a guarantee against account challenges. Buffer's support article explicitly states automated posting through Buffer does not violate LinkedIn's Terms; record this as **Buffer's statement**, not our legal certification. [B LinkedIn]

## Safe handoff, not an exactly-once procurement test

Neither a documented exactly-once guarantee nor access to LinkedIn's restricted member-read API is required merely to consider a managed scheduler. Buffer already provides a readable managed post ledger; Typefully provides readable draft/publication lifecycle. These are materially more useful than assuming write-only self-service creates can always be recovered. [B MCP][T API]

Proposed pilot safety rule: record local content identity, intended profile, approved text/media and schedule before submitting; preserve returned managed ID. Use **one publisher for each slot**, not simultaneous browser + managed attempts. On a timeout/lost create response, mark the attempt **unknown/hold**, list the managed queue/drafts/sent items for the relevant account/time, and inspect plausible matches. A matching item is reconciliation evidence, not a mathematical uniqueness proof; an empty list alone is not permission to recreate. If outcome stays ambiguous, stop that item and use owner/vendor reconciliation—**no blind create retry and no automatic browser fallback**. Known validation rejection is distinct from an uncertain server-side create. Buffer's own guidance explicitly makes this distinction. [B efficiency]

For known-ID publication failure, inspect vendor status/error and connection state before correction or rescheduling; `sending`/`in_progress` is not a failed create. A scheduler acceptance/ID is not evidence the post is already live. Preserve eventual sent/published status and available permalink separately. Cancellation/deletion cannot undo impressions or guarantee winning a race with publication. [B MCP][T API]

## Smallest viable pilot (proposal only)

1. **Human setup once:** with approval to adopt a new service, David creates/uses **Buffer Free**, connects only his personal profile through provider authorization, confirms identity and timezone, and later reconnects if requested. No credentials in chat and no new paid service. If provider authorization is denied, stop and resolve through normal provider/vendor support; do not expand custom hosting as an assumed cure. [B LinkedIn][B pricing]
2. **Reuse accepted calibration:** keep five genuine notes and three accepted private drafts/guide 4; do not restart voice calibration. For one week select three distinct, sourced posts: a genuine college-founder/Callie observation, a cited research/news response with his own analysis, and a concrete real PM decision/tradeoff. Never invent a meeting, metric, customer quote or personal anecdote to fill a slot. Use text-only first unless an approved real image is ready.
3. **Managed handoff:** keep the first editorial batch private. Only after the managed route is selected, integrated and separately activated for the exact account and three/week scope may it schedule ordinary posts; the current production plan is **not activated**. A dashboard pilot can establish vendor behavior, but manual-only handoff is not the permanent replacement for the unattended goal. A rolling one-week queue stays below Free's ten-slot limit. API images need approved stable hosting through publication; dashboard upload alone does not prove programmatic image handoff. [B pricing][B media]
4. **Observe before replacing the host:** establish correct personal author, scheduled automatic publication without a per-post manual publish step, text and one-real-image result, known-ID reads, cancellation of a future disposable draft/slot, and safe hold behavior for ambiguity. Only ordinary real content should go live; no test spam. These are future activation criteria, **not checks performed by this research**. Keep ordinary DMs, comments and likes outside automation scope.

**Decision boundary:** Buffer is the smallest documented no-new-spend candidate; Typefully is credible if its writing/media workflow is preferred, but sustained cadence needs a paid entitlement whose current price must be confirmed before approval. Do not buy either plan or claim host replacement complete until account connection and actual publication are demonstrated. Routine managed autopublication is documented by both; our specific access and operational reliability are not. [B pricing][B scheduling][T pricing][T API]
