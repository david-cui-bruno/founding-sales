# Gmail owner setup and separate capability approval

This procedure prepares ordinary authenticated owner settings for #549 Gmail capture and #550 evidence extraction. It does not authorize activation. The earlier schema88/backlog104 statement was stale: the October 18 readiness handoff reports schema116 and six accepted smoke checks. That is a dated root observation, not a live inspection by this procedure. Root verifies current production/main, deployed adapters and funding before asking David for one exact consent batch. Use [operating state](current-state.md) and the [release procedure](lean-release-workflow.md), not historical schema assertions here, for current release decisions.

## Prepare without activation

1. Sign in normally as the current owner administrator. Connection alone is not consent, and installed desktop credentials must not be repurposed. Do not perform OAuth, provider reads or live UI actions as part of source-only preparation.
2. In Settings → Administration → Evidence extraction setup, reload the current configuration. A new installation starts unconfigured and disabled. No endpoint/model, access/data-handling versions, token prices or budgets are invented. Existing configured values are displayed exactly, including fractional microdollars per token and integer USD-cent daily/monthly ceilings.
3. Root independently verifies the deployed extraction adapter, endpoint, exact model, current access-grant/data-handling versions, exact token prices and funded daily/monthly allowance. The reviewed route list is shared with runtime startup policy. Being on that list is not proof of funding or adapter availability. The Bedrock API endpoint is `bedrock-runtime.us-east-1.amazonaws.com`; `us.*` model IDs are cross-US-region inference profiles, not us-east-1-only inference. Disclose and approve the actual processing/data-use scope. No silent route or card fallback is authorized.
4. Enter only those verified values. The handoff's Haiku4.5, $1/day and $20/month figures are proposals, not live permission or proof of credits. Unknown values stay blank. Select a reviewed route and review every exact field. The save acknowledgment confirms **disabled configuration only**, not capture, processing, spend or backfill consent.
5. Save uses the existing `crm.processingPurposeSave` bridge and `/crm/processing/purpose/save` API. Main owns command ID/client version and authentication. The API checks current membership/administrator access and expected revision. Saving always leaves extraction disabled, increments its revision and clears current authority/owner approval. It neither creates an owner consent audit nor mints an independent authority receipt. It queues no provider work. If already enabled, saving disables extraction, so review that consequence before saving. A stale revision, refused command or uncertain outcome requires reload and fresh review, never blind retry.
6. Reload to inspect durable settings. The separate existing capability controls refresh after a confirmed save. Do not click Activate during preparation. A configuration save cannot bypass capability readiness, exact configuration bindings, quality evidence, access/data handling, current account/generation, runtime funding or source erasure checks. Legacy strict1.0.51 API response shapes remain unchanged.

## Distinct decisions and boundaries

- **Capture:** ongoing copying of qualified or explicitly included incoming and owner-Sent business originals requires its own current mailbox/account/generation, metadata policy, observed OAuth scopes and owner approval. Personal, excluded and unresolved conversations remain excluded. Metadata review is body-free and is not body-read authority.
- **Extraction:** needs/objections/commitments interpretation of authorized copies needs separate exact purpose/model/provider/data/spend approval and #550 evidence. Capture does not authorize hosted AI. Provisional usefulness, actual transport, controlled fixtures and representative quality are distinct claims.
- **Disable:** prevents fresh authorized work but cannot undo accepted provider requests. It retains approved copied history and documentary consent audit. Disconnect stops new capture and does not delete retained copies or grant processing.
- **Deletion:** the explicit scoped deletion flow erases affected Callie copies and dependent evidence, preserves terminal recapture barriers and does not modify Gmail originals. Disable is not deletion, and reconnecting does not restore erased content.
- **Backfill:** historical import requires a separate bounded interval/read allowance and approval. It is excluded from initial capture/extraction setup. Recovery coverage gaps are not proof of complete mailbox history.
- **Other capabilities:** Ask answering, embeddings/indexing, outreach, admission, calling and sending are outside this setup. Plain keyword/record search remains available. No CRM approval grants outreach permission or resumes sending.
