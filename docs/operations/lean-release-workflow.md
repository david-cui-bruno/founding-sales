# Lean production release workflow

Source implementation for #580, 2026-10-11. This document does not lift the current release hold, dispatch a run, apply IAM, or activate a feature.

The supported AWS application production writer is `.github/workflows/greenfield-deploy.yml`, using the existing `fss-production-deploy` concurrency group with cancellation disabled. Application, routine migration maintenance and reviewed Terraform application share that queue. The existing `greenfield-google.yml` production Google apply uses the same queue and literal-false hold; its exact saved-plan review and federated identities remain unchanged. Existing production shell commands allow local preparation and reads but refuse real local cloud writes. This does not prevent a human using raw AWS/Terraform outside the supported workflow; operators must not bypass the queue for routine delivery. Standalone `rollback.sh --apply` is retired for real production: its read-only planning and controlled rehearsal remain available, and repair uses the reviewed workflow.

## Normal delivery

Greenfield remains an always-present required gate. Typecheck and lint run over the repository; pull requests select affected test suites and dependent consumers. Shared/unknown changes fall back to all suites. Main always runs broad regression. Selection and actual command timings are recorded in the job summary; no speed improvement is claimed before measurement.

Release classification starts from observed production builds, not a copied GitHub commit variable or just the last PR. Protected paths touched anywhere in the deployed-to-candidate history remain reviewed even if later reverted. Existing migration blobs must be unchanged byte for byte. Automatic maintenance permits only contiguous explicitly classified additive/routine migrations, with actual disposable-PostgreSQL deployed-to-candidate upgrade evidence bound to those builds. Destructive, privilege-changing, ambiguous and infrastructure work takes review.

`FSS_RELEASE_HOLD` must equal literal `false` before any release branch applies. Missing values mean held. The existing backlog remains held after a source merge. The routine branch uses its separate maintenance identity, observed task definitions, backups and service/network settings; it preserves sending configuration, stores the release record before new workers, drains/stops before migration, verifies schema before restarting, reads the exact record back and checks public health/smoke. No Terraform state rewrite occurs in that branch.

## Reviewed infrastructure or protected changes

Use the same workflow's `review_prepare` mode with the exact green main images run. It can prepare while release is held. The separate read-only planner refreshes the existing production root and writes only its existing Terraform backend locks. It saves a plan, verifies stable live build/service bindings, and uploads a values-free manifest plus encrypted saved plan for one day. The manifest names changed resource addresses/actions, source/image/gate bindings, observed schema, state lineage/serial, PITR inventory and saved-plan checksum. Plaintext plan/state/provider values are not published as artifacts.

Review those concrete resource actions and the manifest fingerprint. One protected `production-release-review` environment approval authorizes the `reviewed` mode with preparation run ID and exact manifest SHA-256. It uses the existing deployment role with explicitly reviewed exact OIDC trust, validates immutable images and unchanged live/state bindings, decrypts the saved bytes, stores the record, stops when required, applies that exact plan, migrates/verifies/restarts and reads back. It never silently regenerates a plan. Changed state/source/configuration requires a new preparation and review.

The saved-plan transport reuses the existing `diagnostic-plan.mjs` encryption implementation rather than adding an authority platform. Deployment approval is not feature activation consent.

## One-time prerequisites before any live use

The source defines `fss-prod-ci-maintenance` and `fss-prod-ci-plan`. The planner does not exist until bootstrap, so its own `review_prepare` mode cannot create it. This is a one-time prerequisite, not a working release path yet. Bootstrap uses the already-existing trusted administrator deployment identity and existing production Terraform root, as a specifically reviewed exception outside the GitHub queue. While the current release hold stays set, first freeze all production writers, observe current build/schema/state, prepare a local saved plan with current image digests and schema ranges, and inspect its exact actions. Limit that plan to creating the two CI roles/policies, the planner listing-only journal policy exemption and additive reviewed OIDC trust, preserving service images, desired counts, sending configuration, secrets and schema. Review the concrete saved-plan checksum and existing trust before a separately authorized application; changed state requires a new plan. Do not copy an invented deployed commit or overwrite the old trust. If Terraform includes unrelated backlog or task-definition changes, refuse it and prepare a narrowly scoped bootstrap plan with those changes excluded and explicitly reviewed. Record actual IAM readback and remove the freeze only after readiness is verified. No bootstrap apply is authorized by this source document. GitHub environment restrictions/secrets also require configuration and readback. The existing `fss-prod-deploy` trust needs the prospective additive statement in `infra/policies/production-reviewed-oidc-trust.json`; retain and review its actual existing trust rather than blindly overwriting it.

Configure main-only `production-maintenance`, `production-plan` and protected `production-release-review` environments. Set the scoped role ARN secrets, `FSS_PRODUCTION_PLAN_PUBLIC_KEY_PEM` variable and protected `FSS_PRODUCTION_PLAN_PRIVATE_KEY_PEM` secret (RSA, at least 3072 bits), plus existing production origin/record settings. Only the reviewed application environment receives the private decryption key. None of these configurations has been applied by the source implementation. Until bootstrap is verified, the new workflow deliberately reports an unmet prerequisite; no local production release or legacy rollback path is a substitute.

## Failure and recovery

Fixed summaries show held/refused/started/completed or repair-required, the actual phase and last observed schema. An ambiguous migration attempt reports schema unknown until inspected. A failed smoke after rollout does not claim rollback or a successful release. Partial writes require observation of actual services/schema/state before forward repair; do not blindly retry a failed saved plan or migration. Workflow summary is not a backup-restoration test: PITR timestamps/retention are measured, restoration remains untested unless separately demonstrated.

Sending caps, recipient eligibility, routine-reply controls, capability consent and evaluation gates remain independent and unchanged. Releasing these sources does not authorize outreach expansion or activate Ask/Gmail.
