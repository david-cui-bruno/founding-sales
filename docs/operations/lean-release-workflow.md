# Lean production release workflow

Sole supported production execution entrypoint. Current observed builds/holds and dated receipts live in [current state](current-state.md), not this procedure. This document does not dispatch a run, lift a hold or activate a feature.

The supported AWS application production writer is `.github/workflows/greenfield-deploy.yml`, using the existing `fss-production-deploy` concurrency group with cancellation disabled. Application, routine migration maintenance and reviewed Terraform application share that queue. The existing `greenfield-google.yml` production Google apply uses the same queue and literal-false hold; its exact saved-plan review and federated identities remain unchanged. Existing production shell commands allow local preparation and reads but refuse real local cloud writes. This does not prevent a human using raw AWS/Terraform outside the supported workflow; operators must not bypass the queue for routine delivery. Standalone `rollback.sh --apply` is retired for real production: its read-only planning and controlled rehearsal remain available, and repair uses the reviewed workflow.

## Normal delivery

### Protected application replacement

The current opt-in branch is `release_mode=application` in [greenfield-deploy.yml](../../.github/workflows/greenfield-deploy.yml), dispatched from `main` with `images_run_id` naming the exact successful push-to-main images run. It uses the protected `production-release-review` environment and the same production queue. A pending approval, returned run ID or source merge is not success. The PR801 private receipt linked from current-state records the actual accepted use of these exact inputs, not a reusable run ID for another release.

Root binds candidate/image/gate identity, inspects actual deployed state and unknown writes, retains fresh recovery and stored-OFF evidence, then approves only the exact owned pending protected run under existing authority. Do not open/change shared repository/environment holds or bypass the environment. Its required reviewer, main-only branch and disabled administrator bypass remain mandatory. Observe the returned run through final workflow/job result, runtime/canary/public smokes, final stored sending check, exact release-record readback and actual cleanup. Public health is not stored-owner consent. Do not redispatch on observer timeout. Application replacement is distinct from Terraform saved-plan application below and never authorizes unreviewed infrastructure.

#### Root application release operator

[`application-release-operator.mjs`](../../infra/scripts/application-release-operator.mjs) replaces per-release private operators: `node infra/scripts/application-release-operator.mjs <preflight|observe-off|verify-off|verify-application> --dir <private run directory>`, in that order. The directory, outside the repository, holds `release-bindings.json` (`runId`, `jobId`, `gateId`, `imagesId`, `candidate`, `prNumber`, `prHead`, `upgradeJobId`; run/job stay `null` until dispatch; optional `migrationReview`), later `application-native-input.json` (actual rendered final status), `main-images/image-digests.json` and, for a migration, the main gate's `main-upgrade/` evidence. Each step refuses existing outputs and writes with exclusive create. `preflight` derives the baseline commit/schema, definitions, counts and digests from live production and saves it; later steps bind to that file, never re-derive. Only `observe-off` writes: one reviewed reader register/run/retire, custody first, one attempt each, unknown outcomes inspected, never retried.

Same-schema sources touch no schema/migration path. Otherwise only one contiguous N→N+1 migration is accepted: candidate `REQUIRED_SCHEMA` exactly N+1, exactly one new migration file, every deployed migration blob unchanged, and the bound main upgrade artifact proving a passing disposable-PostgreSQL N→N+1 upgrade. Its classifier result is recorded: `additive` proceeds; `touches-existing` requires `migrationReview` (`reviewer`, `report`, `classification`) matching it; privilege, destructive, replaced-routine, unclassified, multi-step or evidence-less changes refuse and take the reviewed path. `verify-application` then requires native `migrationStarted`, N→N+1 schemas, five retired readers, the contiguous drain/idle/auth/prepare/verify/record/drain-off tasks and PITR pinned before DDL. Dispatch and approval stay with Root above.

Do not merge to `main` while a dispatched release runs: the job refuses `dispatch_main_changed` after its first writes. A refused migration release can leave circuit-breaker rollback disabled, a drain that expires by itself within an hour, and never-deployed candidate task definitions that become the latest revisions and make the next OFF reader refuse `operations_image_changed`. Repair before a new run directory: restore rollback to the Terraform baseline, wait for the drain to end, and deregister only those candidate definitions.

Greenfield remains an always-present required gate. Typecheck and lint run over the repository; pull requests select affected test suites and dependent consumers. Shared/unknown changes fall back to all suites. Main always runs broad regression. Selection and actual command timings are recorded in the job summary; no speed improvement is claimed before measurement.

Release classification starts from observed production builds, not a copied GitHub commit variable or just the last PR. Protected paths touched anywhere in the deployed-to-candidate history remain reviewed even if later reverted. Existing migration blobs must be unchanged byte for byte. Automatic maintenance permits only contiguous explicitly classified additive/routine migrations, with actual disposable-PostgreSQL deployed-to-candidate upgrade evidence bound to those builds. Destructive, privilege-changing, ambiguous and infrastructure work takes review.

Automatic application delivery, routine maintenance and the Google writer require `FSS_RELEASE_HOLD` to equal literal `false`; missing values mean held. A source merge does not lift that shared admission hold. The separately approved reviewed job below does not require or change any repository/environment hold. The routine branch uses its separate maintenance identity, observed task definitions, backups and service/network settings; it preserves sending configuration, stores the release record before new workers, drains/stops before migration, verifies schema before restarting, reads the exact record back and checks public health/smoke. No Terraform state rewrite occurs in that branch.

## Reviewed infrastructure or protected changes

Source choices are not permission to change IAM or perform a backend transaction.

Use the same workflow's `review_prepare` mode with the exact green main images run. It can prepare while release is held. The separate read-only planner refreshes the existing production root and writes only its existing Terraform backend locks. It saves a plan, verifies stable live build/service bindings, and uploads a values-free manifest plus encrypted saved plan for one day. The manifest names changed resource addresses/actions, source/image/gate bindings, observed schema, state lineage/serial, PITR inventory and saved-plan checksum. Plaintext plan/state/provider values are not published as artifacts.

Review those concrete resource actions and the manifest fingerprint. One protected `production-release-review` environment approval authorizes only that exact `reviewed` run with preparation run ID and exact manifest SHA-256, while shared holds remain unchanged. The environment must enforce its required reviewer, main-only deployment branch and disabled administrator bypass. This reuses the existing approval, not an additional owner ceremony. Before credentials, the job verifies the exact preparation dispatch/repository/workflow/commit, manifest and immutable images. Only its subsequent execute step sets process-local `FSS_RELEASE_HOLD=false` for the existing script guards and child processes. No workflow/job-wide override, `$GITHUB_ENV` export, variable-write credential or repository/environment variable mutation is needed. Automatic/maintenance/Google writers stay held, including runs queued while the reviewed job executes. Operator disconnection cannot leave a shared release window open.

It uses the existing deployment role with explicitly reviewed exact OIDC trust, validates unchanged live/state bindings, decrypts the saved bytes, stores the record, stops when required, applies that exact plan, migrates/verifies/restarts and reads back. It never silently regenerates a plan. Changed state/source/configuration requires a new preparation and review. Operators must retain direct returned run IDs, full input bindings, fresh PITR and stored sending OFF evidence before approving. Do not reuse a historical launcher that opens/restores shared holds: the next operator must dispatch and approve without changing them. This source change does not create that private operator or dispatch a release.

The saved-plan transport preserves the existing encryption implementation in `release-plan-transport.mjs` rather than adding an authority platform. Deployment approval is not feature activation consent.

Preparation and reviewed application must be dispatched from main at the same exact dispatch commit, with the successful completed preparation run belonging to this repository and workflow. That dispatch identity is separate from the selected immutable images commit: a docs/workflow-only main update does not relabel older verified images. The approved manifest, image run, gate run, digests and upgrade evidence remain bound to the images commit. If main advances between preparation and application, prepare and review again. The reviewed job requests only a one-hour session from the existing deployment role; it does not increase the role's maximum or extend authorization on expiry. The job's longer timeout is not a credential lifetime guarantee; an expired session is a failure requiring actual-state observation before any repair.

### Audited admin one-offs (Root)

Commands marked "audited ECS launcher required" (`discovery configure`, `discovery resume`, `qualification configure`, `targeting configure`, `research set-ceilings`, …) refuse `launcher_unknown` unless they run as an ECS task on the production `operations` definition with `FSS_LAUNCHED_BY` set to the launching principal; the command reads its own task ARN from ECS metadata and audits both. Root runs them with the existing production role through `release_run_task` (`infra/scripts/lib.sh`) on the current normal operations definition: the latest ACTIVE `fss-prod-operations` revision, whose single `operations` image must equal the image every running `fss-prod-worker` task runs, while `/health` `build.commit` equals the expected deployed commit (the release operator's normal-definition check). Any mismatch is NO-GO, launching nothing. `fss admin research status --workspace-id <ws>` is read-only and needs no launcher; run it first for current research settings, spend, firm runs, worst-case run cost, discovery settings and search-account usage. Run the pattern below as a script or subshell from the repository root: the `lib.sh` helpers `exit` on refusal.

```bash
source infra/scripts/lib.sh
release_read_root infra/roots/production fss-prod production "runs an audited admin one-off on production's database"
expected=<deployed commit, from current-state>
who=$(aws sts get-caller-identity --query Arn --output text)
# Terraform's operations_task_definition_arn can name an older revision than hosted releases registered:
# use the latest ACTIVE fss-prod-operations revision, held to the image the running worker tasks run.
td=$(aws ecs describe-task-definition --task-definition fss-prod-operations --output json)
ops=$(jq -r '.taskDefinition.taskDefinitionArn' <<<"$td")
img=$(jq -er 'select(.taskDefinition.status=="ACTIVE" and (.taskDefinition.containerDefinitions|length)==1 and .taskDefinition.containerDefinitions[0].name=="operations") | .taskDefinition.containerDefinitions[0].image' <<<"$td") || { echo "NO-GO: operations definition shape"; exit 1; }
running=$(aws ecs describe-tasks --cluster "$CLUSTER_ARN" --tasks $(aws ecs list-tasks --cluster "$CLUSTER_ARN" --service-name fss-prod-worker --desired-status RUNNING --query 'taskArns' --output text) \
  --query 'tasks[].containers[?name==`worker`].imageDigest[]' --output text | tr '\t' '\n' | sort -u)
[ -n "$running" ] && [ "$(wc -l <<<"$running")" -eq 1 ] && [ "${img#*@}" = "$running" ] || { echo "NO-GO: operations image ${img#*@} is not the running worker image"; exit 1; }
[ "$(curl -fsS --max-time 10 https://api.usecallie.com/health | jq -r '.build.commit')" = "$expected" ] || { echo "NO-GO: /health build.commit is not $expected"; exit 1; }
release_run_task --step admin-<name> --environment "$ENVIRONMENT" --prefix "$PREFIX" --account "$ACCOUNT" --region "$REGION" \
  --cluster "$CLUSTER_ARN" --task-definition "$ops" --container operations \
  --network-plan "$NETWORK_PLAN" --image-digest "${img#*@}" --database-host "$DATABASE_HOST" --secret-arn "$RUNTIME_SECRET_ARN" \
  --log-group "$LOG_GROUP" --log-stream-prefix operations --capture "/tmp/admin-<name>.log" --env "FSS_LAUNCHED_BY=$who" \
  -- admin research set-ceilings --workspace-id <ws> --owner-user-id <active admin> --daily-cents <n> --monthly-cents <n> \
     [--daily-firms <n>] [--approval-ref "<who approved, when>"] --report /tmp/fss-admin.json
```

Any increase of a research ceiling needs `--approval-ref`; the `research.ceilings_set` audit records before/after, approval, owner, launcher and task ARN. Record the task ARN and JSON answer, and reconcile a task whose outcome is unknown before any retry.

## Failure and recovery

The shared hold controls automatic admission; it is not instantaneous revocation of a protected run already approved for exact execution. To stop it, reject its pending approval or cancel the exact owned hosted run through existing GitHub controls. Cancellation can leave provider/migration writes unknown. Contain sending, inspect actual state and fix forward, never blindly replay. Local observation failure is not hosted failure/cancellation. Final status must describe the actual job even while shared holds remain set. Current stored owner OFF stays OFF. Only a healthy release removes its own temporary block for already-authorized sending after fresh checks, preserving owner-disabled controls/newer stops. This is not per-release reapproval of unchanged consent, nor permission to enable a stored OFF switch.

Fixed summaries show held/refused/started/completed or repair-required, the actual phase and last observed schema. An ambiguous migration attempt reports schema unknown until inspected. A failed smoke after rollout does not claim rollback or a successful release. Partial writes require observation of actual services/schema/state before forward repair; do not blindly retry a failed saved plan or migration. Workflow summary is not a backup-restoration test: PITR timestamps/retention are measured, restoration remains untested unless separately demonstrated.

Sending caps, recipient eligibility, routine-reply controls, capability consent and evaluation gates remain independent and unchanged. Releasing these sources does not authorize outreach expansion or activate Ask/Gmail.

### Explicit never-started reader reconciliation

For an observed failed application release whose exact candidate is already running at the same schema, `application` accepts optional `failed_reader_custody` JSON. Blank leaves ordinary behavior unchanged. The protected environment and production queue remain mandatory. This is not a tail-resume or an automatic retry. Root retains the failed run's actual status and approves only the new exact run after current runtime, stored-OFF, holds and unknown-write observations.

Supply exactly four string keys from the original failed-run custody and normal operations definition, never a guessed adjacent revision:

```json
{"taskArn":"<exact failed reader task ARN>","readerDefinitionArn":"<exact temporary operations definition ARN>","startedBy":"fss-app-<failed run ID>-off-<sequence>","sourceOperationsDefinitionArn":"<original normal operations definition ARN>"}
```

Input identity is not cleanup authority. Hosted execution refreshes the failed run's provenance, both definitions' prior application-role registration identity, exact native `offRead` transformation and generated task overrides, allowing only the optional extra `inferenceAcceleratorOverrides: []`. Null/populated collections, other keys and environment/role/command changes refuse. Only the exact actual STOPPED `TaskFailedToStart`/`CannotPullContainerError` task with no start/exit evidence qualifies. Its declared digest-pinned image must match the source. Any actual image digest present must also match; an absent digest is not pulled-image or successful-OFF proof. Unknown starts/outcomes, changed definitions/owners, foreign tasks and other failures remain held without cleanup.

Reference proof covers API and worker service definitions/deployments plus complete bounded RUNNING and desired-STOPPED cluster task inventories. Incomplete/paginated/ambiguous observations and unexpected active tasks refuse. This deliberately relies on Root's supported two-service inventory and exclusive production ownership, not proof that no dormant third-party service exists. No IAM expansion, service update or task stop belongs to reconciliation.

After refreshed gates and custody, execution requests deregistration of that one reader definition once, with native CLI retries disabled only for that exact command, verifies INACTIVE and exact normal-family resolution, then discards the explicit source override and repeats all normal definition, OFF, recovery, schema, rollout, runtime/canary/public-smoke and exact record-readback checks. Existing promoted image tags/digests are required; reconciliation cannot republish images. Preserve original image/gate identities and the full record payload, including `gate.updated_at`. A changed payload conflicts rather than replacing history. `readerRecovery` retains exact custody and observing/deregister-requested/completed state. An unknown deregistration outcome remains repair-required without another request. Current-run reader failure/cleanup semantics are unchanged.

### Explicit historical read-only definition retirement

An aged-out task does not satisfy the preceding never-started predicate. A separate exact five-key custody shape adds `"evidenceBasis":"historical-readonly-retirement"` to those four identity strings. There is no implicit fallback on a missing task, and other discriminator values/keys refuse. Root must explicitly select this basis under existing protected release authority. It authorizes only definition retirement, not a historical task outcome or permission to dispatch.

This branch supports only audited source `bced9eebcc4c3fef4ee51d7eefd0f92e66f318c7`, failed run40522197864/attempt1/application job122252105573, task `a91d7da900aa401789560498b29d7b12`, reader337/source335 and same running schema142. Hosted execution fetches the original run/attempt, complete bounded job inventory, exact job metadata and native timestamped job log through existing GitHub read access. It validates the original execution/finalizer step identities and conclusions, finalizer timestamps, immutable image/gate bindings and one complete, unambiguous original custody status. Missing, duplicate, truncated, conflicting, wrong-step/attempt or unsupported-source evidence refuses. No manually written receipt, supplied log bytes, container-log absence or later workflow's status semantics can replace these reads. The audited read-only script bytes are also pinned, so changing the shared reader requires a new source review.

The original combined identity/exit/digest assertion failed. Its STOPPED response does **not** prove that the returned task identity matched. Authenticated original source/status establish generated launch intent and custody only. Current exact-task observation must contain only an empty task array and the exact ARN's sole `MISSING` failure; this means unavailable history, never terminal, never-started, successful OFF or no effects. Available or conflicting task data refuses this branch rather than weakening the live predicate.

Retirement requires all preceding current source/reader registration, exact native read-only definition, latest-family, running candidate/image and freshly repeated complete two-service/deployment/task no-reference checks. A missing target appearing in inventory, any nonterminal reader reference, unexpected active workload or incomplete inventory refuses. The same explicit exclusive-owner/two-service assumptions apply. One deregistration, unknown-write custody, INACTIVE/normal-family readback and the entire normal forward release remain unchanged, including fresh OFF/zero-dispatching and independent unknown-write checks. No task replay/stop or image republish is allowed.

`readerRecovery` records the selected basis, original attempt/job, audited source and retirement progress, with `historicalExecution` and `historicalEffects` explicitly `UNKNOWN`, even after retirement completes. The old run remains failed. Retirement cannot resolve another unknown provider effect, assert historical no-effects, restore sending or bypass final OFF/smoke/record acceptance. The original never-started review does not cover this consequential predicate change. It requires focused ordinary and production-risk review before CI/use.

Unknown responses retain custody and require inspection; no retry or task stop. An observation failure remains held and must not be blindly rerun. The subsequent full recovery retains every normal retirement/release/PITR/smoke/final-OFF/record requirement above.
