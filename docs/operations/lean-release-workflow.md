# Lean production release workflow

Sole supported production execution entrypoint. Current observed builds/holds and dated receipts live in [current state](current-state.md), not this procedure. This document does not dispatch a run, lift a hold or activate a feature.

The supported AWS application production writer is `.github/workflows/greenfield-deploy.yml`, using the existing `fss-production-deploy` concurrency group with cancellation disabled. Application, routine migration maintenance and reviewed Terraform application share that queue. The existing `greenfield-google.yml` production Google apply uses the same queue and literal-false hold; its exact saved-plan review and federated identities remain unchanged. Existing production shell commands allow local preparation and reads but refuse real local cloud writes. This does not prevent a human using raw AWS/Terraform outside the supported workflow; operators must not bypass the queue for routine delivery. Standalone `rollback.sh --apply` is retired for real production: its read-only planning and controlled rehearsal remain available, and repair uses the reviewed workflow.

## Normal delivery

### Protected application replacement

The current opt-in branch is `release_mode=application` in [greenfield-deploy.yml](../../.github/workflows/greenfield-deploy.yml), dispatched from `main` with `images_run_id` naming the exact successful push-to-main images run. It uses the protected `production-release-review` environment and the same production queue. A pending approval, returned run ID or source merge is not success. The PR801 private receipt linked from current-state records the actual accepted use of these exact inputs, not a reusable run ID for another release.

Root binds candidate/image/gate identity, inspects actual deployed state and unknown writes, retains fresh recovery and stored-OFF evidence, then approves only the exact owned pending protected run under existing authority. Do not open/change shared repository/environment holds or bypass the environment. Its required reviewer, main-only branch and disabled administrator bypass remain mandatory. Observe the returned run through final workflow/job result, runtime/canary/public smokes, final stored sending check, exact release-record readback and actual cleanup. Public health is not stored-owner consent. Do not redispatch on observer timeout. Application replacement is distinct from Terraform saved-plan application below and never authorizes unreviewed infrastructure.

Application replacement and reviewed saved-plan execution both create the canonical immutable CI record with `enablesSending:false`; neither grants sending authority. The deployment `FSS_SENDING_ENABLED` flag is checked independently by production smoke. Reusing a gate/commit identity must reuse the same record; a different payload remains a conflict, never an overwrite or authorization fallback.

Root's temporary stored sending pause uses the normal `POST /settings/update` command. Retain the pre-pause enabled value/version and the pause receipt's `previousVersion`/new version; if the receipt did not replace that exact enabled version, it grants no restoration authority. After healthy release acceptance and fresh readiness/consent/unknown-write checks, restore only with `expectedVersion` equal to that owned pause version. The API compares it under the existing send-gate/setting locks and returns `setting_version_conflict` without a write after any intervening edit, including another OFF. Leave a newer control unchanged; never rebind the expected version or retry as an unconditional enable. Explicit owner saves may omit the condition and retain normal last-write-wins semantics.

#### Root application release operator

[`application-release-operator.mjs`](../../infra/scripts/application-release-operator.mjs) replaces per-release private operators: `node infra/scripts/application-release-operator.mjs <preflight|observe-off|verify-off|verify-application> --dir <private run directory>`, in that order. The private directory holds `release-bindings.json` (`runId`, `jobId`, `gateId`, `imagesId`, `candidate`, `prNumber`, `prHead`, `upgradeJobId`, `offVersions`; run/job remain `null` until dispatch; optional `migrationReview`), later actual rendered `application-native-input.json`, immutable `main-images/image-digests.json` and any `main-upgrade/` evidence. Pin `offVersions` to the actual paused sending-setting versions before preflight, not a source constant; missing/invalid versions, rebinding or a later stop refuse. This does not authorize resuming owner-disabled sending. Each step refuses existing outputs and writes exclusively. Preflight derives/saves actual baseline commit/schema/definitions/counts/digests and pinned inputs; later steps bind to that observation. Only `observe-off` writes: one reviewed reader register/run/retire, custody first, one attempt each; inspect unknown outcomes, never retry.

Same-schema sources touch no schema/migration path. Otherwise only one contiguous N→N+1 migration is accepted: candidate `REQUIRED_SCHEMA` exactly N+1, exactly one new migration file, every deployed migration blob unchanged, and the bound main upgrade artifact proving a passing disposable-PostgreSQL N→N+1 upgrade. Its classifier result is recorded: `additive` proceeds; `touches-existing` requires `migrationReview` (`reviewer`, `report`, `classification`) matching it; privilege, destructive, replaced-routine, unclassified, multi-step or evidence-less changes refuse and take the reviewed path. `verify-application` then requires native `migrationStarted`, N→N+1 schemas, five retired readers, the contiguous drain/idle/auth/prepare/verify/record/drain-off tasks and PITR pinned before DDL. Dispatch and approval stay with Root above.

Both `preflight` and the hosted application job refuse, before any write, when RDS `fss-prod-pg` is `backing-up` or the release would start inside, or within 120 minutes (the job's 110-minute timeout) before, its UTC `PreferredBackupWindow` or `PreferredMaintenanceWindow` (`backup_window_near`, `maintenance_window_near`; an unparsable window refuses as `*_window_unreadable`), because the later recovery pin refuses a `backing-up` instance only after services are drained and stopped; the hosted job repeats the check with a fresh read just before suppressing rollback.

Do not merge to `main` while a dispatched release runs: the job refuses `dispatch_main_changed` after its first writes. A refused migration release can leave circuit-breaker rollback disabled, a drain that expires by itself within an hour, and never-deployed candidate task definitions that become the latest revisions and make the next OFF reader refuse `operations_image_changed`. Repair before a new run directory: restore rollback to the Terraform baseline, wait for the drain to end, and deregister only those candidate definitions.

Greenfield remains an always-present required gate. Typecheck and lint run over the repository; pull requests select affected test suites and dependent consumers. Shared/unknown changes fall back to all suites. Main always runs broad regression. Selection and actual command timings are recorded in the job summary; no speed improvement is claimed before measurement.

Release classification starts from observed production builds, not a copied GitHub commit variable or just the last PR. Protected paths touched anywhere in the deployed-to-candidate history remain reviewed even if later reverted. Existing migration blobs must be unchanged byte for byte. Automatic maintenance permits only contiguous explicitly classified additive/routine migrations, with actual disposable-PostgreSQL deployed-to-candidate upgrade evidence bound to those builds. Destructive, privilege-changing, ambiguous and infrastructure work takes review.

Automatic application delivery, routine maintenance and the Google writer require `FSS_RELEASE_HOLD` to equal literal `false`; missing values mean held. A source merge does not lift that shared admission hold. The separately approved reviewed job below does not require or change any repository/environment hold. The routine branch uses its separate maintenance identity, observed task definitions, backups and service/network settings; it preserves sending configuration, stores the release record before new workers, drains/stops before migration, verifies schema before restarting, reads the exact record back and checks public health/smoke. No Terraform state rewrite occurs in that branch.

### Audited admin one-offs (Root)

Commands marked "audited ECS launcher required" (`discovery configure`, `discovery resume`, `qualification configure`, `targeting configure`, `research set-ceilings`, …) refuse `launcher_unknown` unless they run as an ECS task on the production `operations` definition with `FSS_LAUNCHED_BY` set to the launching principal; the command reads its own task ARN from ECS metadata and audits both. Root runs them with the existing production role through `release_run_task` (`infra/scripts/lib.sh`) on the current normal operations definition: the latest ACTIVE `fss-prod-operations` revision, with the normal CLI shape (entryPoint `["node","apps/worker/src/tools/fss.ts"]`, command `["verify"]`, as the release operator's `normal_cli_changed` check requires), whose single `operations` image must equal the image every running `fss-prod-worker` task runs, while `/health` `build.commit` equals the expected deployed commit (the release operator's normal-definition check). Any mismatch is NO-GO, launching nothing. `fss admin research status --workspace-id <ws>` is read-only and needs no launcher; run it first for current research settings, spend, firm runs, worst-case run cost, discovery settings and search-account usage. Run the pattern below as a script or subshell from the repository root: the `lib.sh` helpers `exit` on refusal.

```bash
source infra/scripts/lib.sh
release_read_root infra/roots/production fss-prod production "runs an audited admin one-off on production's database"
expected=<deployed commit, from current-state>
who=$(aws sts get-caller-identity --query Arn --output text)
# Terraform's operations_task_definition_arn can name an older revision than hosted releases registered:
# use the latest ACTIVE fss-prod-operations revision, held to the image the running worker tasks run.
td=$(aws ecs describe-task-definition --task-definition fss-prod-operations --output json)
ops=$(jq -r '.taskDefinition.taskDefinitionArn' <<<"$td")
img=$(jq -er 'select(.taskDefinition.status=="ACTIVE" and (.taskDefinition.containerDefinitions|length)==1 and .taskDefinition.containerDefinitions[0].name=="operations"
  and .taskDefinition.containerDefinitions[0].entryPoint==["node","apps/worker/src/tools/fss.ts"] and .taskDefinition.containerDefinitions[0].command==["verify"]) | .taskDefinition.containerDefinitions[0].image' <<<"$td") \
  || { echo "NO-GO: not the normal operations CLI definition (a leftover OFF-reader revision replaces entryPoint and clears command)"; exit 1; }
running=$(aws ecs describe-tasks --cluster "$CLUSTER_ARN" --tasks $(aws ecs list-tasks --cluster "$CLUSTER_ARN" --service-name fss-prod-worker --desired-status RUNNING --query 'taskArns' --output text) \
  --query 'tasks[].containers[?name==`worker`].imageDigest[]' --output text | tr '\t' '\n' | sort -u)
[ -n "$running" ] && [ "$(wc -l <<<"$running")" -eq 1 ] && [ "${img#*@}" = "$running" ] || { echo "NO-GO: operations image ${img#*@} is not the running worker image"; exit 1; }
[ "$(curl -fsS --max-time 10 https://api.usecallie.com/health | jq -r '.build.commit')" = "$expected" ] || { echo "NO-GO: /health build.commit is not $expected"; exit 1; }
release_run_task --step admin-<name> --environment "$ENVIRONMENT" --prefix "$PREFIX" --account "$ACCOUNT" --region "$REGION" \
  --cluster "$CLUSTER_ARN" --task-definition "$ops" --container operations \
  --network-plan "$NETWORK_PLAN" --image-digest "${img#*@}" --database-host "$DATABASE_HOST" --secret-arn "$RUNTIME_SECRET_ARN" \
  --log-group "$LOG_GROUP" --log-stream-prefix operations --capture "/tmp/admin-<name>.log" --env "FSS_LAUNCHED_BY=$who" \
  -- admin research set-ceilings --workspace-id <ws> --owner-user-id <active admin> --daily-cents <n> --monthly-cents <n> \
     [--daily-firms <n>] [--approval-ref "<who approved, when>"] --report /tmp/fss-admin.json
```

Any increase of a research ceiling needs `--approval-ref`; the `research.ceilings_set` audit records before/after, approval, owner, launcher and task ARN. Record the task ARN and JSON answer, and reconcile a task whose outcome is unknown before any retry.

## Failure and recovery

The shared hold controls automatic admission; it is not instantaneous revocation of a protected run already approved for exact execution. To stop it, reject its pending approval or cancel the exact owned hosted run through existing GitHub controls. Cancellation can leave provider/migration writes unknown. Contain sending, inspect actual state and fix forward, never blindly replay. Local observation failure is not hosted failure/cancellation. Final status must describe the actual job even while shared holds remain set. Current stored owner OFF stays OFF. Only a healthy release removes its own temporary block for already-authorized sending after fresh checks, preserving owner-disabled controls/newer stops. This is not per-release reapproval of unchanged consent, nor permission to enable a stored OFF switch.

Fixed summaries show held/refused/started/completed or repair-required, the actual phase and last observed schema. An ambiguous migration attempt reports schema unknown until inspected. A failed smoke after rollout does not claim rollback or a successful release. Partial writes require observation of actual services/schema/state before forward repair; do not blindly retry a failed saved plan or migration. Workflow summary is not a backup-restoration test: PITR timestamps/retention are measured, restoration remains untested unless separately demonstrated.

Sending caps, recipient eligibility, routine-reply controls, capability consent and evaluation gates remain independent and unchanged. Releasing these sources does not authorize outreach expansion or activate Ask/Gmail.
