# Ask architecture: empirical paper evidence

Research date: October 10, 2026. Scope: primary papers and their released implementations relevant to CRM conversation retrieval and model-led investigation. This is literature evidence, not a Callie model run, release decision or activation receipt. No paid model calls were made.

## Recommendation from the evidence

Use a **single bounded, read-only tool-using model with progressive evidence access** as the default architectural direction for cross-record Ask questions. Give it exact CRM-state reads, lexical search, semantic search when available, and full conversation/evidence reads. Keep a direct full-thread route for questions already scoped to a small conversation. Preserve PostgreSQL as authoritative state and keep acquisition, authorization, deletion and source-version checks outside model discretion.

This is a design inference, not a demonstrated Callie performance result. Published work is enough to reject the idea that we must invent a complicated retrieval workflow before building Ask. It is not enough to choose a universal winning model, runtime or latency target. A small local smoke evaluation remains useful as implementation verification, rather than claiming to discover the best general architecture from 20 homemade cases.

## Architectural consequences for Callie

These are recommendations from comparing the evidence, not settled product changes or paper claims about our code.

1. **Make evidence acquisition adaptive, not every subsystem agentic.** Ask can choose reads; mailbox synchronization, durable writes and deletion keep explicit application contracts. A model cannot decide an email is actually sent from language alone.
2. **Expose progressive tools.** Search should return short, dated, attributed previews plus stable source/version identifiers. A separate read expands a conversation with speaker, sent/received direction and neighboring context. Domain tools resolve identities and current tasks/opportunities. Avoid arbitrary SQL or shell tools for end users.
3. **Keep direct context when the relevant thread is known.** Model-led investigation need not mean an unnecessary search loop for “summarize this conversation.” Complete chronology helps preserve promise/correction/quote context.
4. **Use semantic retrieval as an additional search capability.** The papers support complementary lexical and semantic access, not a requirement for a separate vector database. PostgreSQL plus an eligible semantic index remains consistent with the approved architecture; embeddings should not become an authority for exact state.
5. **Bound the loop and return useful partial answers.** Deadlines, maximum reads/tokens, recoverable errors and deduplication belong in the runtime. Allow a richer investigation only when evidence is incomplete. Do not claim researched latency targets as achieved measurements.
6. **Record evidence, not hidden reasoning.** Trace public tool arguments/results, versions and answer citations. Final output must distinguish captured facts, inference, conflicts and absent coverage. Recheck authorization/source validity before returning evidence or committing changes.
7. **Do not start with multi-agent, GraphRAG or trained self-reflection machinery.** None of the reviewed sources establishes that extra complexity as necessary for our present sparse CRM corpus. Keep extension seams if corpus/task complexity later warrants them.

## What research settles, and what it cannot

The literature gives us a defensible direction: a capable model with a small tool surface and reliable execution substrate, selective fuller context, and hybrid search where beneficial. It does not supply a matched benchmark of Callie's identity rules, shared mailboxes, historical relationships, quoted email, explicit commitments and deletion contracts.

A public benchmark should be used as external evidence and optional regression material. The existing synthetic pack should check those missing domain failure modes and tool integration; it should not be marketed as a universal architecture bake-off. Actual real-business quality remains unavailable until representative conversations accumulate. That limitation does not block building useful capture, timeline, manual CRM or a disabled Ask implementation.

No reviewed evidence changes the release hold, sending permissions, recipient scope, caps, automatic-admission controls or capability-specific activation gates. This note proposes no experiment execution authority.
