# Cal.com booking capacity evidence and acceptance

Research checked October 8, 2026 for #453 / #441. This note records supported reads and acceptance; it is not a live provider configuration receipt, backend release or signed desktop publication.

## What Cal.com supports

Cal.com's current event-type read requires `cal-api-version: 2026-06-12` and bearer authentication. It returns an event's identity, owner, booking URL and `bookingLimitsCount`, including the `week` setting. OAuth access to the individual event read requires `EVENT_TYPE_READ`. A version mismatch can select older behavior, so an unversioned read is insufficient evidence for this implementation. [Get an event type](https://cal.com/docs/api-reference/v2/event-types/get-an-event-type)

The event-type list accepts `username` plus `eventSlug`; the slug alone is insufficient because separate users can have the same slug. This implementation reads only a simple personal approved Cal.com URL with exactly those two path segments. It requires exactly one returned event, matching slug, URL and owner. Team, routing, private, custom-domain and ambiguous links need a separately verified access/mapping path; no personal-owner guess is made. The list also requires version `2026-06-12`. [List event types](https://cal.com/docs/api-reference/v2/event-types/list-event-types)

`GET /v2/me` returns the authenticated account's ID and username. OAuth access needs `PROFILE_READ`. Successful account and event reads establish access for those reads; possession of an API key or a webhook secret does not itself prove the intended account or configuration. Tokens, secret contents, provider error prose and unrelated profile fields are never response evidence. [Get my profile](https://cal.com/docs/api-reference/v2/me/get-my-profile), [Access control](https://cal.com/docs/api-reference/v2/access-control)

Event limits apply to one event type. Global user limits cover bookings across personal and team event types; Cal.com makes periods unavailable after the applicable accepted-booking limit is reached, and resets periods using the user's timezone. `GET /v2/me/booking-limits` can read global limits, but it is restricted to organization members; a `403` may mean a non-organization account. OAuth needs `PROFILE_READ`. This source slice does not probe global limits or infer account membership from a forbidden response. [User booking limits](https://cal.com/docs/api-reference/v2/user-booking-limits), [Get my booking limits](https://cal.com/docs/api-reference/v2/me/get-my-booking-limits)

## What Callie shows

Three introductory calls per week remains David's preference, with enforcement explicitly unverified. A successful owned event read shows the configured weekly limit for that approved booking link only. An absent, disabled or unknown weekly setting is not a verified limit. A cap on one event type does not establish a combined limit across all introductory-call links or remaining availability.

The read uses existing calendar routing and `outreach_settings.booking_url`, independently of routine-reply activation. A missing link/key, invalid key, inactive/ambiguous routing, unsupported URL, wrong account/event, missing/ambiguous event, invalid answer or provider refusal produces coded missing evidence. A setting revision or routing change during the provider read invalidates its result. The transport performs two bounded GET reads, follows no redirects and submits no appointment/configuration changes.

Saved booking records come from the existing verified-webhook/reconciliation state machine, with its source update time. They retain matched versus unresolved/ambiguous context, cancellation/reschedule/attendance state and workspace scope. Matched records are visible to their assigned salesperson or an administrator; unresolved attendee addresses are hidden from salespeople. Projection happens after the remote read and uses current assignment and active membership role in one database query. Reassignment or administrator demotion during that read removes former access, and inactive membership returns no booking records. A bounded saved list is not a complete provider calendar, a count of introductory calls, current slot availability or enforcement proof. Refresh failure does not prove that no bookings exist.

2. Read the approved URL and current calendar routing, then the authenticated account and exact event configuration through the documented versions. Save a metadata-only receipt with observation time, account/event association, URL binding, weekly setting, result and source commit. Retain missing/forbidden/ambiguous results honestly.
3. Verify which links are actually approved for introductory calls. A verified three/week event setting covers only that event. Any claim covering all introductory calls needs evidence that all relevant event types are covered, or an applicable verified global user limit with its account/timezone scope. Unknown other links leave the combined preference unverified.
4. For an enforcement claim, retain actual provider configuration/grant evidence and confirm provider availability behavior at the applicable weekly limit using an authorized non-prospect test or existing evidence. Do not manufacture real appointments or modify live settings merely to complete the test. Any configuration change requires its own reviewed authorization and subsequent readback.
5. Verify the integrated API/desktop view, current matching ambiguity, ownership and truthful unavailable states. Controlled transport/PostgreSQL/component tests establish source behavior; normal backend release and signed desktop acceptance remain separate gates.
