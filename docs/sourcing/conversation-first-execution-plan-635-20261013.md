# Conversation-first execution plan

October 13, 2026. Final coordinator synthesis for research decision #635 under [Conversation-first unattended execution readiness map](https://github.com/david-cui-bruno/founding-sales/issues/606). This is planning, not a declaration of live readiness.

## Destination and canonical decisions

New qualified property-manager conversations come first. Coordinated email and LinkedIn prospecting, credible original posting, agreed-call booking and useful evidence-backed CRM/Today/Ask support that funnel. David handles substantive sales replies, negotiations and calls. Connection acceptance, a reply, a booking, attendance and a qualified conversation are separate observations, not guaranteed quotas.

Policy detail remains in the canonical decision tickets, not duplicated here: [standing authority](https://github.com/david-cui-bruno/founding-sales/issues/607), [posting](https://github.com/david-cui-bruno/founding-sales/issues/608), [booking](https://github.com/david-cui-bruno/founding-sales/issues/609), [full conversational Ask](https://github.com/david-cui-bruno/founding-sales/issues/610#issuecomment-6150473491), and [LinkedIn runtime policy](https://github.com/david-cui-bruno/founding-sales/issues/634#issuecomment-6149951302).

## Execution classification

| Classification | What it means | What it does not mean |
| --- | --- | --- |
| AFK source work | Existing ticket, agreed behavior, bounded caller/worker tests, one owner per shared boundary | Permission to send, acquire private data, deploy or spend on a new scope |
| Controlled evidence | Normal authenticated callers/registered workers, real disposable PostgreSQL, controlled external/native adapters | Actual provider/native/model usefulness or installed/deployed acceptance |
| Bounded operational preparation | Exact proposed account/data/model/budget/command/plan and privacy-safe expected readback | Blanket approval of task registration, infrastructure writes, current identity or live readiness |
| Actual observation | Authorized real scope, correct identities/current revisions, retained result and cleanup | Representative reliability, unrestricted access or approval of a changed scope |
| Release/Enable | Applicable exact candidate approval, reviewed release and independently passing configured scope | Global clearance of other capabilities or customer response guarantee |

## Conversation-first work order

1. **Evidence recovery:** finish the existing retained prospect-loss and disabled-email readiness tracks. Recover original records, do not use fresh acquisition or reshaped historical receipts as substitutes. Stop at missing artifacts or unavailable safe access. The research reports linked below decide whether source extensions are actually needed.
2. **Parallel source frontier:** supported LinkedIn routes, versioned outreach policy and connection/manual-activity observations are independent. Posting drafts/policy and booking interpretation/creation/policy can proceed independently where file ownership permits. Discovery/email source fixes are eligible only after a demonstrated defect, not an assumed parser failure.
3. **Actual consumed dependencies:** LinkedIn conversation capture follows supported routes. Invitations and accepted-connection openers both consume policy, observations and reply/refusal capture; existing accepted connections make opener work independent of invitation implementation. The coordinated lifecycle joins those paths before actual activation. Booking and posting retain their already-published native graphs.
4. **Integration:** one coordinator owns shared schema/contracts, Person/Firm/source access and deletion, cross-channel history/reservations, policy/account revisions and accounting. Workers own disjoint files or explicitly sequenced shared-boundary changes. A native graph with no blocker does not permit concurrent writes to the same shared file.
5. **Verification:** caller-facing TDD, no invented red/green, relevant local checks, exact-head CI and independent Spec/Standards reviews before normal merges. Confirm no unapproved rollout/Enable can result from a merge. Preserve the paused Ask narrowing and all prior uncertain actions.
6. **Deployment and operation:** prepare the exact bootstrap/release packet, then obtain the required concrete approval. Bind each capability's actual account/data/purpose/provider/model/recurring budget through normal setup and readback. Enable only independently passing scopes; continue safe independent work when another lane is held.
7. **Useful outcomes:** observe actual supported inflow, delivery uncertainty, replies/stop/handoff and agreed bookings separately. Measure retained-model quality/cost/latency and installed-native outcomes separately from source completion. No fixed customer-response milestone blocks engineering.

## Explicit remaining checkpoints

- Recoverable original discovery arrays/provenance and truthful unavailable historical clock/input limits through a supported exact-case read.
- A genuinely safe runtime/control/sender read executor. Nominal readiness/control/standing calls may maintain sender state; a READ ONLY database transaction does not make its surrounding cloud launcher side-effect-free.
- Fresh serving identity and applicable draft-exclusion/legacy-handoff proof. The existing source repair is not a new activation API or fresh deployed evidence.
- Authentic evaluation/release/smoke and owner/mailbox/sequence/render/configuration bindings, not invented verifier-ready JSON.
- Selected LinkedIn account/session, supported layout and capture/connection/manual/reply coverage; one original voice sample calibration before live scope, not per-recipient review.
- Actual booking account/event/availability and scoped logistics provider configuration; no automatic sales negotiation or guessed agreement.
- Core capture, interpretation, hosted Ask and optional indexing account/data/purpose/retention/provider/model/recurring-budget readback. Posting/booking/DM/diagnostic approvals are not silently transferable to those scopes.
- Concrete protected production packet approval, required login/OS permissions and physical-device observations. Existing native acceptance tickets remain owners of actual evidence.

These are bounded acceptance/access/approval checkpoints, not automatically missing source contracts or blanket dependencies on every lane.

## Research and ticket-slicing conclusion

The coordinator reviewed all three reports and independently checked original-observation storage/read code, the serialized-production-writer policy, the local write refusal and the official ECS execution-mode constraint. No required product outcome lacks an existing execution owner, and no new source ticket is justified by the selected-only export or intentional standing-read maintenance.

The original normalized arrays are persisted and can potentially be recovered from the exact retained run, but survival/access and original historical clock/input completeness are unverified. Existing admin reads are not an exact-run minimal projection. The existing noninteractive operations mechanism can run some read commands, but no currently sanctioned executor covers the complete selected diagnostic scope without cloud task operations. Old launchers cannot be reused as zero-write reads.

One sharp decision remains: [Choose the supported transport for bounded evidence inspection](https://github.com/david-cui-bruno/founding-sales/issues/636). Alternative A prepares an exact owner-reviewed one-off inspection packet under the existing setup/deployment owner, including an explicit narrowly bounded operating-policy exception. Alternative B proposes one small supported serialized-workflow inspection slice. Neither is executable now, neither lifts release/sending holds, and no new implementation ticket is published before approval. This gates only the affected live evidence recovery, not independent source work.

The to-tickets result is therefore **zero unconditional new source slices**. Preserve the already-published frontier. If the owner chooses B, the proposed single tracer must supply both the scoped documentary command and the supported transport, rather than a pure-read helper with no usable execution path. Existing prospect-loss and disabled-email tickets still own consumed evidence/replay; setup/deployment owns operation authority and actual configured execution. Do not duplicate the draft repair, manufacture a parser violation or create an architecture/observability program.
