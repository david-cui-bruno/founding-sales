## What readonly can acquire

| Requested content | Provider capability and constraint |
| --- | --- |
| Retained message bodies | `gmail.readonly` allows `messages.get`. `full` returns parsed MIME; `raw` returns the encoded RFC message. `gmail.metadata` cannot return bodies. Broader modify or full-mail scopes are unnecessary for capture. [Message get](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get), [Formats](https://developers.google.com/workspace/gmail/api/reference/rest/v1/Format) |
| Threads | Readonly allows `threads.get` with full message data. A thread fetch can include messages outside a selected historical window; keeping those is a scope choice. [Thread get](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.threads/get) |
| Labels | Readonly allows label listing; message label IDs distinguish mailbox state. Labels can differ between messages in the same thread. [Label list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.labels/list), [Message list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list) |
| Spam and Trash | Listing supports explicit `includeSpamTrash=true`. Inclusion is a product decision, not a new scope. Permanently vanished content cannot be reconstructed by enumerating current resources. [Message list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list) |
| Drafts | Readonly allows `drafts.get`. A draft is unsent; its stable draft ID contains a message whose ID changes on replacement. Sending deletes the draft and creates a new Sent message. This API is not a prior-draft-version archive. [Draft get](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.drafts/get), [Draft lifecycle](https://developers.google.com/workspace/gmail/api/guides/drafts) |
| Attachment bytes | Readonly allows `messages.attachments.get`. A MIME part may carry inline `data` or an `attachmentId` requiring a separate fetch; fetching `full` alone does not guarantee all bytes are inline. Base64url decoding and per-part byte size are explicit. [Attachment get](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages.attachments/get), [MessagePartBody](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages.attachments) |

“All history” must therefore mean a stated coverage of currently retrievable messages and subsequent observed changes, not every message or draft version that ever existed. The public listing contract states no 90-day historical cutoff: that window is Callie's prior product scope. List returns IDs/thread IDs, up to 500 per page, with an estimated count; exhaustive coverage requires exhausting page tokens and fetching content. Queries are optional and unavailable under metadata-only scope. [Listing contract](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list)

History is a change stream, not an archival content endpoint. It supports additions, deletions, label additions and label removals. IDs increase with gaps; stale cursors return404 and require full synchronization. History is usually available at least a week but can be shorter. A long historical acquisition must preserve an initial anchor, reconcile concurrent changes and recover expiration without claiming snapshot completeness. [History list](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list), [Synchronization guide](https://developers.google.com/workspace/gmail/api/guides/sync)

Current quotas distinguish older projects from projects subject to the May2026 table. Published new limits are6,000 units/user/project/minute and1.2million/project/minute; message get and attachment get cost20 each, thread get40, list5 and history list2. The page still describes later2026 billing as planned and an80million daily threshold. Actual project limits and applicable billing remain unknown. Message/attachment byte counts, duplicate reads and backoff affect duration; no mailbox-volume or completion-time estimate was measured. No universal attachment-download size ceiling is specified by the attachment-get contract checked here; Gmail sending limits must not be misrepresented as a capture limit. [Quota contract](https://developers.google.com/workspace/gmail/api/reference/quota)

## Policy boundary

Google explicitly permits email clients, automatic email backup, CRM/productivity features and generative summaries. One-time/manual email-export applications and multi-account abuse are disallowed. Data use must serve prominent appropriate features; transfers need consent and an allowed purpose. Human access is restricted; generalized AI training beyond the specific user's personalized appropriate feature is prohibited. Disclosure must precede affirmative collection consent; deletion controls are required. Encryption, secure transport, prompt-injection protection and restricted-scope security requirements apply. The policy also contains a permanent-copy/cache warning. These rules neither prohibit all hosted inference nor authorize arbitrary hosted use, unlimited retention or collection for hypothetical future features. [Workspace user-data policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)

The linked API Terms §5e qualifies permanent-copy/database/cache prohibitions with express content-owner permission or applicable law; §5a addresses rights in third-party content; §5d requires comparable portability while data is stored. The approved backup use and sync guide's caching guidance do not establish Callie's specific indefinite-retention basis. Review the actual permission/rights basis, retention purpose, export/deletion behavior and provider contractual handling before activation. Ordinary OAuth disconnection is not identical to termination of API access under §8b. No legal conclusion is established here. [API Terms](https://developers.google.com/terms), [Sync caching guidance](https://developers.google.com/workspace/gmail/api/guides/sync)

`gmail.readonly` is restricted; public apps require restricted-scope verification, and server storage/transmission normally requires security assessment. Documented exceptions include properly configured internal organizational apps and personal/testing cases, with their specific conditions. One owner does not establish internal status; an existing working token proves neither verification nor assessment. Callie's actual OAuth distribution, app approval and assessment evidence were not inspected. [Scope classifications](https://developers.google.com/workspace/gmail/api/auth/scopes), [Verification exceptions](https://support.google.com/cloud/answer/13464323)

## Current source limits, separate from Google constraints

- One active mailbox per workspace owner is still enforced by `mailboxes_one_per_owner` in `packages/domain/db/migrations/0009_mail.sql:82`; connection/re-consent updates that row via `ON CONFLICT (workspace_id, owner_user_id)` in `packages/domain/mail/mailboxes.ts:214`. Multiple owners can have separate mailbox rows. Concurrent multiple Google accounts for one owner need a new model and access/authority design.
- Migration0026 permits `personal` and `cold_outreach` kinds while retaining the shared-mailbox refusal. Migration0027's `mailbox_accounts` records historical intervals of in-place account switches; it is not multiple concurrent OAuth connections. Provider identity/generation remains part of acquisition and source access.
- `packages/domain/mail/gmailClientHttp.ts:324` always constructs bounded epoch-date listing queries and explicitly includes Spam/Trash. Ordinary recovery requests draft exclusion in `recover.ts:464`. This is not an unbounded complete-history enumerator.
- `gmailClientHttp.ts:94` caps normalized bodies at100,000 characters; `readRepresentation` skips filename/attachment-ID parts and marks partial/truncated content. This is Callie's representation limit, not Gmail's. Metadata attachment references do not establish copied/parsed attachment coverage.
- The October8 research's additions-only history finding is now stale: the adapter optionally requests/parses all four change kinds at `gmailClientHttp.ts:594`; `crmHistoryRecovery.ts:128` enables lifecycle changes. Ordinary paths retain their own policy and behavior.
- ADR0006 keeps source identity and deletion barriers; it distinguishes inclusion, body acquisition and hosted processing. ADR0009 binds independently reviewed capability authority to exact owner/account/configuration/evidence. General capture cannot fabricate operational contact matches, sending authority or processing grants.

## Decisions the interview must settle

Specify simultaneous mailbox count/owners; historical date coverage; Inbox/Sent/archive versus Spam/Trash/drafts; normalized searchable text versus original MIME and attachment bytes; continued synchronization; and source retention/deletion after Gmail removal or disconnect. These are product choices subject to the provider constraints above, not defaults implied by readonly scope or the existing business-capture approval.
