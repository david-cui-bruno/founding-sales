## Five findings

1. **Weekly means draft generation, not publishing authority.** `packages/domain/social/weekly.ts:15-24,32-60` exposes an owner toggle with expected-revision concurrency, audit, weekly queueing, no catch-up batches and draft-request limits. Changing settings invalidates queued periodic work (`:26-30`). `packages/domain/social/draftPolicy.ts:21-37` restricts model input to generic themes/approved facts, forbids DM/scheduling/publication instructions and explicitly says David reviews every draft; `:53-69` validates constrained output. Current policy is per-post review, not standing authorization.

2. **Post approval is exact and revision-bound.** `packages/domain/social/posts.ts:14-23,25-46` saves revisions, freezes destination identity/revision, content, media and future time into a fingerprint, and creates approval/delivery for that revision. Edits invalidate pre-submission work; uncertain/submitting/scheduled/cancellation-pending posts cannot be edited (`:17-22`). Tests in `packages/domain/test/social/approvals.test.ts:13-37` cover stale revisions, fingerprint change and cancellation pending. There is no revocable versioned standing-policy approval contract in the inspected social route/contracts/source; #608 itself frames it as a new contract.

3. **Account identity and local disconnect are modeled; cloud authority is not.** `packages/domain/social/accounts.ts:7-29` supports the native LinkedIn adapter, rejects identity mutation and records account observation; `:31-38` increments revision and disconnects locally while preserving remote-schedule receipts/cancellation state. The source feasibility note, dated 2026-10-09 against source `157b1afd`, says native only, no OAuth cloud adapter, and OAuth grants/refresh entitlement/account-specific pricing are unverified, not proven absent: `docs/sourcing/linkedin-cloud-publication-feasibility-20261009.md:19-23`. The same note proposes authorization/readback and cost/access gates before any cloud path (`:25-33`). No credential inspection was done.

4. **Native desktop scheduling has a real queue/recovery seam, but acceptance is incomplete.** API caller contract is `apps/api/src/routes/social.ts:24-59` (weekly/drafts/accounts/posts/approval/cancel/queue/claim/begin/observe); weekly UI-to-operation seam is `apps/desktop/src/main/operationHost.ts:236-254` and `apps/desktop/src/shared/operations.ts:922-923`. Desktop wires account-scoped Electron LinkedIn check/open and the delivery pump in `apps/desktop/src/main/app.ts:294-314`. Domain tests `packages/domain/test/social/delivery.test.ts:10-29,39-49` cover single-claim, durable submission marker, inspect-not-replay, uncertain outcomes and restart queue visibility. Desktop tests include `apps/desktop/test/socialDeliveryRunner.test.ts` and `socialRecovery.test.ts` (controlled source tests, not provider proof).

5. **Current source contains no LinkedIn connection-request or DM workflow.** The focused social API contract lists manual destination/account connect-disconnect and post/delivery actions, with no connection invitation, inbox/reply, DM send, opt-out or reply-stop route (`apps/api/src/routes/social.ts:24-59`). Draft generation explicitly excludes DMs (`packages/domain/social/draftPolicy.ts:37`). This is a bounded source finding, not a claim that no other external/manual workflow exists. `docs/sourcing/linkedin-automation-architecture-research.md:11,36-44` distinguishes publishing from outreach vendor designs; it is dated research, not native provider evidence.
